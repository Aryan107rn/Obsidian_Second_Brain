Start here

What system design means

System design is deciding which parts a software system needs, what each part owns, how the parts communicate, and how the design meets real requirements as the system grows.

Code level

Inside a component

Functions, data structures, algorithms, and local correctness.

System level

Between components

Services, databases, networks, data flow, failure handling, and operational cost.

Think in problems first. “Reads are slow and repeated” suggests looking at indexes or caching. It does not automatically mean “add Redis.” Tie every component to a requirement or a bottleneck.

The toolkit

Core building blocks

A typical request travels through a small set of parts. Start simple and add pieces when a need appears.

Entry and delivery

DNS finds the service address. CDN serves cacheable content near users. Load balancers route requests to healthy instances.

Compute and communication

Application services enforce business rules. Queues buffer work that can happen later; consumers process it with retries and idempotency.

Data and speed

Databases keep durable records. Caches hold disposable, fast copies. Object storage fits large files and blobs.

Operations

Metrics, logs, and traces reveal behavior. Health checks, alerts, backups, and deployment controls help teams recover safely.

What “good” means

Quality attributes

Make the target explicit. “Fast” and “reliable” are not measurable until you define them.

QualityMeaningExample question
LatencyTime for one operation to complete.What is the p95 feed response target?
ThroughputOperations handled per unit of time.How many writes arrive per second at peak?
AvailabilityFraction of time a service is usable.Can reads continue if one zone fails?
ReliabilityCorrect behavior over time, including under failure.Can a retry create a duplicate payment?
DurabilityCommitted data survives failures.Can an acknowledged upload be lost?
ConsistencyWhen and how replicas show updates.Must a new post appear instantly to every follower?
ScalabilityAbility to handle growth in load or data.What becomes the bottleneck at 10× traffic?
CostResources and operational effort used.Is the latency gain worth extra replicas?
A repeatable method

End-to-end design process

A good design conversation is a sequence of decisions backed by requirements and rough numbers.

Clarify scope

List core user actions and explicitly defer secondary features. Ask about users, regions, privacy, and expected growth.

Write measurable requirements

Separate functional behavior from targets such as p95 latency, availability, durability, consistency, and cost.

Estimate the load

Estimate requests per second, read/write ratio, peak multiplier, data growth, and bandwidth. State assumptions out loud.

Define APIs and data

Sketch the key endpoints, request/response shapes, entities, ownership, indexes, and access patterns.

Draw the simplest architecture

Show clients, entry point, service, durable store, and external dependencies. Trace a write and a read end to end.

Find bottlenecks, then scale

Use the estimates to identify pressure. Add cache, replicas, partitions, queues, or regional routing only when they address it.

Design for failure and operation

Discuss timeouts, retries, duplicate requests, overload, failover, backups, monitoring, security, and recovery.

Explain trade-offs and evolve

Compare options, name what is eventually consistent, and describe a sensible first version and its next scaling step.

Back-of-the-envelope

Capacity estimation

Approximate numbers are useful when they expose the shape of the problem. Precision is less important than clear assumptions.

Example assumptions: 1 million daily active users, each makes 20 feed reads and 2 posts per day; 10× peak over average; average stored post metadata is 1 KB.

EstimateCalculationApproximate result
Daily reads1M × 2020M / day
Average read QPS20M ÷ 86,400≈ 231 / sec
Peak read QPS231 × 10≈ 2,310 / sec
Daily posts1M × 22M / day
Metadata per year2M × 1 KB × 365≈ 730 GB / year raw

Remember: raw storage excludes indexes, replicas, backups, and media bytes. Ask whether average rate hides bursts, and whether image/video storage dominates metadata.

Engineering judgment

Common choices and trade-offs

ChoiceHelps withCosts / risks
Cache a readLower latency and database loadStale values, invalidation, stampedes
Read replicasRead scale and regional readsReplication lag; writes still hit primary
Queue background workFast responses and burst absorptionDelayed completion, retries, duplicate delivery
Shard dataMore write/storage capacityCross-shard queries and resharding complexity
DenormalizeFewer joins and faster readsMore copies to update consistently
Multi-regionLower geographic latency and regional resilienceConflict resolution, replication, operating cost
Before you finish

Design review checklist

Requirements

□ Scope and exclusions stated
□ Targets are measurable
□ Load assumptions are visible

Architecture

□ APIs and data model defined
□ Read/write paths traced
□ Each component has a reason

Resilience

□ Timeouts and retries considered
□ Idempotency for repeatable writes
□ Failover, backups, and recovery

Operations

□ Metrics, logs, traces, and alerts
□ Security and access boundaries
□ Costs and next bottleneck discussed
